# MiniMind Agentic RL 过程记录：Reward 修复、Tool SFT、Agent RL 与 Hard Eval

日期：2026-05-07  
项目目标：在 MiniMind 上优化 Agentic RL / tool-use 能力，建立可复现的 `rollout -> reward -> SFT/RL -> eval` 闭环。

---

## 1. 阶段性结论

当前最重要的结论是：

1. `tool_sft_v4_patch` 是目前基础 33 条 eval 上的最佳 checkpoint。
2. `agent_tool_v1` 证明了 RL 训练链路已经跑通，但基础 eval 指标与 `tool_sft_v4_patch` 完全持平，没有新增收益。
3. 原因不是 RL 代码没跑通，而是基础 RL 数据太小、太简单，`tool_sft_v4_patch` 已经接近 reward 饱和。
4. 新构造的 hard eval 成功暴露了 SFT 的真实短板：多步工具调用、hard distractor、参数构造和最终答案使用仍明显不足。
5. 下一步不应继续刷基础 33 条 eval，而应扩展干净、可执行、可验证的 hard SFT / hard RL 数据，并分离 train/eval。

## 2. 关键代码修改记录

### 2.1 修复数字答案误判

问题：

早期 `answer_contains_expected()` 使用 substring 判断数字答案，导致：

```text
expected_answer = "25"
final_answer = "根号 625 是 390625。"
```

被误判为正确，因为 `"25"` 出现在 `"625"` / `"390625"` 中。

修改：

- 增加数字抽取 regex。
- 对 `expected_answer_type == "number"` 禁止 substring 匹配。
- 使用 `math.isclose()` 做数值近似匹配。
- 默认容差：`rel_tol=1e-3`，`abs_tol=1e-2`。

新增测试：

- `25` 不应匹配 `625` / `390625`。
- `62.137` 可以匹配四舍五入后的 `62.14`。
- `18 squared is 324.`、`13的平方是169。`、`有6个字符` 都能正确抽数。

---

### 2.2 修复 observation 使用评测

问题：

早期 `obs_use_acc` 对工具 observation 使用判断过于粗糙：

- 时间工具返回 `2026-05-05 20:49:27`，模型回答 `2026年5月5日20时49分27秒` 时可能被误判没用 observation。
- `text_length` 同时返回 `characters` 和 `words`，模型把 `words=2` 的任务答成 `characters=10` 时，仍可能因为使用了 observation 中某个数字而拿到 `obs_use_reward`。

修改：

- 增加 `_obs_value_used(final_answer, value)`。
- 数值 observation 使用数值近似匹配。
- datetime observation 支持中英文时间格式。
- 增加可选字段 `expected_obs_keys`，例如：

```json
{"text_length": ["words"]}
```

含义：该任务只认可模型使用 `text_length.words`，不认可使用 `characters`。

当前本地注意点：

AutoDL 上 hard eval 第一次运行发现 `expected_obs_keys` 存在但当前工具名没有对应 key 时会报错：

```text
TypeError: 'NoneType' object is not iterable
```

AutoDL 已手动热修为：

```python
default_obs_keys = ["result", "datetime", "characters", "words"]
keys = expected_obs_keys.get(tool_name) if expected_obs_keys else None
keys = keys or default_obs_keys
if isinstance(keys, str):
    keys = [keys]
```

建议后续正式合入本地代码，并添加测试覆盖：

- `expected_obs_keys` 非空但不包含当前 `tool_name` 时不崩溃。
- `expected_obs_keys[tool_name]` 为字符串、列表、空值时都有兜底。

---

### 2.3 增加 no-tool 过度调用惩罚

问题：

基础 no-tool 样本中模型有时会在不需要工具时调用工具。

修改：

在 `compute_total_reward()` 中增加：

```python
"unnecessary_tool_penalty": -0.5 if "unnecessary_tool" in metrics["failures"] else 0.0
```

并在 `aggregate_reward_infos()` 中加入该字段。

新增测试：

- no-tool 任务直接回答应比调用工具后回答 reward 更高。

### 3.3 Agent RL v1 训练现象

训练命令从 `tool_sft_v4_patch` 开始：

```bash
python train_agent.py \
  --rollout_engine torch \
  --from_weight tool_sft_v4_patch \
  --save_weight agent_tool_v1 \
  --data_path ../dataset/agent_rl_tooluse.jsonl \
  --batch_size 1 \
  --num_generations 2 \
  --tool_env_mode guarded \
  --device cuda \
  --epochs 1 \
  --learning_rate 3e-7 \
  --save_interval 50 \
  --num_workers 0
```

现象：

- RL 流程跑通：rollout、reward、policy update、save、eval 都可运行。
- 多个 step 出现 `Low reward variance`，`GrpStd=0`，`AdvStd=0`。
- 说明基础 28 条 RL 数据过小、过易，GRPO/CISPO 组内 advantage 经常塌缩。

结论：

`agent_tool_v1` 是 RL 闭环成功的证据，不是性能更优模型。

## 5. 下一步建议

### 5.1 先正式合入两个工程修复

必须合入：

1. `reward.py` 的 `expected_obs_keys` 兜底逻辑。
2. `run_tool_eval.py` 的 `--continue_on_error`。

建议新增测试：

- `expected_obs_keys` 字典非空但不包含当前 observation tool 时不崩溃。
- `run_tool_eval` 单条 eval exception 可以记录为 `eval_exception`。

---

### 5.2 扩大 hard 数据并拆分 train/eval

当前 hard 数据只有 31 条，只适合作为 smoke / first attempt。

推荐扩展为：

| Split | Size | Purpose |
|---|---:|---|
| `tool_eval_hard.jsonl` | 100-200 | holdout eval |
| `tool_sft_hard_train.jsonl` | 500-1500 | hard SFT |
| `agent_rl_tooluse_hard_train.jsonl` | 500-1500 | hard RL |

原则：

- train 和 eval 不共享相同 prompt / ID。
- 继续保持可执行、可验证。
- 优先补 multi-step、hard distractor、field selection、no-tool-with-tools。
- 暂不引入需要动态 verifier 的随机数依赖任务。

---

### 5.3 先做 hard SFT，再做 hard RL

原因：

hard eval 的 `tool_acc=0.4839`、`args_acc=0.5484` 偏低，说明模型连工具选择和参数构造都还不稳。此时直接 RL 信号会比较噪。

建议路线：

```text
tool_sft_v4_patch
  -> hard SFT mixed training
  -> tool_sft_v6_hard
  -> hard/basic eval
  -> Agent RL
  -> agent_tool_v2_hard
```

hard SFT 训练集建议混合：

```text
dataset/tool_sft_small_v4_patch.jsonl
dataset/tool_sft_hard_train.jsonl
```

避免 hard SFT 提升 hard eval 的同时损坏基础能力。

---

### 5.4 再做 Agent RL

只有当 `tool_sft_v6_hard` 在 hard eval 上明显改善，且基础 eval 不退化时，再跑 RL。

建议参数：

```bash
cd /root/minimind/trainer

OMP_NUM_THREADS=1 python train_agent.py \
  --rollout_engine torch \
  --from_weight tool_sft_v6_hard \
  --save_weight agent_tool_v2_hard \
  --data_path ../dataset/agent_rl_tooluse_hard_train.jsonl \
  --batch_size 1 \
  --num_generations 4 \
  --tool_env_mode guarded \
  --device cuda \
  --epochs 1 \
  --learning_rate 1e-7 \
  --max_gen_len 384 \
  --thinking_ratio 0.0 \
  --save_interval 50 \
  --num_workers 0
```

评测时同时看：

```text
basic eval 是否退化
hard eval 是否提升
failure_counts 是否减少
GrpStd=0 是否下降
```
